# Why Most AI Agents Break the Moment They Leave the Demo
<!-- angle: Agencies are shipping agent demos that fall apart on day two in production. I run these for clients, and the failures are boring and predictable: no guards, no state, no cost ceiling. Here is the pattern and what I would do instead. -->

## HOOK
Last month I watched an AI agent delete three weeks of a client's CRM notes because a vendor's API returned an empty list instead of an error. The demo had been flawless. This is the part nobody shows you, and I think it is the only part that matters.
## SCENE: office at night, computer screen glowing | software dashboard close up
Here is my claim. Most AI agents do not fail because the model is dumb. They fail because the people who built them treated a demo as a product. A demo runs once, on a happy path, with a human watching. A product runs ten thousand times, on every path, with nobody watching. Those are different engineering problems, and in my experience almost every agency pitch deck quietly pretends they are the same.
## SCENE: flowchart drawing on whiteboard | engineer sketching diagram
Let me define the thing first, because the word agent gets stretched. An agent is a loop. The model reads a goal, picks a tool, reads the result, and picks again until it decides it is done. That loop is the whole trick, and it is also the whole risk. Every pass through the loop is a chance to misread a result, and the misreadings compound. A chatbot gets one shot at being wrong. An agent gets forty.
## SCENE: domino chain falling | cascading failure abstract
That compounding is the first failure I see in the wild. In the CRM story, the API returned an empty list because the client's auth token had expired. The model read empty as true, concluded there were no notes to keep, and ran the cleanup step it had been told to run. Nothing in that chain was a hallucination. Every step was locally reasonable. The system was wrong because nobody told it that empty can mean broken.
## SCENE: hand pressing emergency stop button | red warning light industrial
So my first rule, and I would put it above everything else: an agent needs a guard that is not the model. Not a sentence in the prompt that says be careful. A piece of code that refuses to run a destructive tool unless the preconditions are checked, in code, by something that cannot be talked out of it. I have audited builds where the only thing standing between the agent and a mass delete was the phrase please confirm before deleting. A sentence is not a guard. A sentence is a hope.
## SCENE: server racks data center | cables network infrastructure
The second failure is state. Demos are stateless because they are short. Production agents run for minutes or hours, and they need to remember what they already did, what they already tried, and what the user already said no to. I have watched an agent retry the same failing call eleven times because nothing recorded that it had failed ten times already. The model was not stupid. It had amnesia, and we gave it the amnesia by not writing anything down between steps.
## SCENE: notebook with handwritten log | person writing checklist
The fix is unglamorous. Write a record for every step. What tool, what input, what came back, what it cost. Make the agent read that record before it chooses the next step. In the builds I run, this one change cut retry loops almost to zero, and it had a side effect I did not expect. When something does go wrong, you can read the log and see exactly where the reasoning bent. Without it, every incident is a mystery novel.
## SCENE: taxi meter running | money counter spinning
The third failure is money. Every loop iteration costs tokens, and a loop with no exit condition costs tokens forever. I have seen a single stuck agent spend more in an afternoon than the client's monthly plan. The vendors will tell you to set a maximum number of steps, and you should, but I would go further. Set a dollar ceiling per task, enforced in code, and make the agent stop and ask when it hits it. A task that is worth two dollars should not be allowed to spend two hundred.
## SCENE: hourglass sand running out | loading spinner close up
There is a cousin of the money problem that I almost never see handled, and that is time. A tool call that hangs is not an error to the model. It is silence, and the loop will wait for it forever unless something outside the loop says enough. In one build I reviewed, a single stalled webhook kept an agent alive for six hours, billing the whole time, doing nothing. Every tool call needs a timeout, and the timeout needs to be reported back to the model as a result it can reason about, not swallowed as if nothing happened.
## SCENE: two people disagreeing at a table | hands gesturing conversation
Now, the counterargument, because it is a fair one. Some people say all of this is premature. Models are getting better every quarter, so why build scaffolding that the next release makes unnecessary? I disagree, and here is why. The failures I just described are not model failures. A perfect model still cannot know that your auth token expired unless something tells it. A perfect model still spends money on every step. Scaffolding is not a patch for a weak model. It is the part of the system that stays true when the model changes.
## SCENE: architect reviewing blueprints | building plans on desk
Anthropic's own guidance on building agents makes a point I keep coming back to. The most successful deployments they saw used simple, composable patterns rather than elaborate frameworks, and they added autonomy only where it clearly paid for itself. OpenAI's agent documentation says something similar in different words: start with a single agent and a small tool set, measure, then expand. I read both of those as a warning against the thing most agencies are selling, which is maximum autonomy on day one.
## SCENE: craftsman testing a tool | quality inspection workshop
So what would I actually do? Here is the checklist I now hand to every client before we build anything. One, list every tool the agent can call and mark the ones that can destroy or spend. Two, put a code-level guard in front of each of those, with preconditions that do not depend on the model's judgment. Three, log every step to a store the agent reads back. Four, cap steps and cap dollars per task. Five, run it against the ugly inputs first, the empty lists, the timeouts, the malformed responses, before you ever run it against the happy path.
## SCENE: before and after comparison split screen | progress chart rising
When we did this for the CRM client, the rebuild took nine days. The agent now does less than the demo promised. It will not delete anything on its own, it asks when a result looks empty, and it stops at five dollars a task. The client is happier with the smaller agent than they ever were with the bigger one, because the smaller one has never once surprised them. I think that is the actual product. Not autonomy. Predictability.
## SCENE: question mark neon sign | thinking person silhouette
One more thing I would push back on. There is a popular idea that you can prompt your way to safety, that if you write a long enough system prompt the agent will behave. I have tested this directly, and it does not hold. A prompt shapes the typical case. It does nothing for the edge case, and production is nothing but edge cases wearing a trench coat. If a rule matters, it goes in code. If it does not matter enough to go in code, be honest that it is a preference, not a rule.
## OUTRO
If you are evaluating an agent build right now, ask the vendor three questions. What stops it from running a destructive tool, and is that thing code or a sentence? What does it remember between steps? What happens at the hundredth dollar? If any of those answers is a shrug, you are buying a demo. I will keep posting what I learn from these builds, including the ones that go wrong, because that is where the useful lessons live. Thanks for watching.
